# PlotPilot 可信创作闭环落地建议

## 背景与判断

PlotPilot 当前已经具备长篇小说创作所需的关键能力：Story Bible、知识图谱、三元组、伏笔账本、章节生成、全托管 Autopilot、张力诊断、一致性检查、章节元素分析等。问题不是能力不足，而是这些能力仍像分散工具箱，尚未形成稳定、可解释、可控的创作闭环。

下一阶段产品目标应从“继续新增 AI 工具”转向“建立可信创作工作流”：让作者清楚知道 AI 本次依据什么生成、生成结果是否可信、哪里有风险、下一步应该怎么修，以及哪些内容可以安全进入长期记忆。

## 产品定位

建议定位为：

> 长篇小说 AI 总编工作台：结构化世界记忆 + 可监管自动写作流水线 + 章节级质量审稿。

不建议继续强调“全自动写完整本小说”。更准确的承诺是：帮助作者低成本完成规划、起草、诊断、修订、一致性维护和连续创作。

## 核心原则

1. 未确认内容不能强污染长期记忆。
2. 自动生成必须可解释、可暂停、可回滚。
3. 诊断结果必须转化为可处理任务，而不是只展示报告。
4. 每章都应该有明确状态和进入下一章的质量门禁。
5. Bible、知识图谱、伏笔、张力等能力应围绕“本章下一步”服务，而不是分散入口。

## 目标用户

### 核心用户

长篇网文、类型小说、同人小说作者。他们需要稳定产出大量章节，同时维护人物、设定、伏笔、时间线、节奏和章节连续性。

### 次核心用户

小说工作室、编辑型作者、AI 写作重度用户。他们关心批量生产、章节审稿、质量看板、改稿效率和设定一致性。

### 暂不优先覆盖

只想一句话生成短篇或轻量娱乐文本的小白用户。当前产品功能密度高，更适合严肃项目型创作。

## 当前主要体验断点

### 1. Autopilot 不可信

用户看到的是“启动全托管”，但实际可能出现章节截断、上下文漂移、质量波动。用户不知道系统当前依据了哪些上下文、为什么继续推进、是否已经检测到风险。

### 2. 生成、诊断、修订割裂

张力诊断、一致性报告、伏笔账本、知识图谱都能指出问题，但缺少统一的“问题处理流”。用户看到问题后不确定该改正文、改 Bible、接受新设定、重跑生成，还是忽略。

### 3. 上下文污染不可见

旧摘要、错误三元组、污染角色名可能进入 prompt。用户通常在成文后才发现主角名漂移或设定错位。

### 4. 一致性报告信任成本高

误报会快速降低用户信任。报告需要证据链、置信度、来源和处理动作，否则用户会逐渐忽略所有警告。

### 5. 章节状态不够产品化

现在章节有 draft/completed 等状态，但缺少创作流程意义上的状态闭环，例如待审、需修订、已锁定、已入库。

## 建议的信息架构

### 项目驾驶舱

展示整本书进度、当前卡点、待审章节、严重一致性问题、未闭合伏笔、Autopilot 状态、质量趋势。

### 章节工作台

作为日常主入口：

- 左侧：章节树与章节状态。
- 中间：正文编辑、生成草稿、修订 diff。
- 右侧：本章写作依据、质量审稿、问题任务、下一步动作。

### 设定中心

Story Bible、知识图谱、角色、地点、世界观、风格设定。日常不应要求用户频繁进入，而是由问题任务跳转编辑。

### 质量中心

跨章节质量审查：角色弧线、伏笔回收、张力曲线、节奏异常、设定冲突、上下文污染趋势。

### Autopilot 控制台

展示自动驾驶当前阶段、上下文包、风险、下一步动作、可暂停点、回滚点和用户批准项。

## P0：章节可信闭环

### 目标

先保证“稳定写完一章并知道能不能进入下一章”。这是后续监管式 Autopilot 和长期记忆卫生的基础。

### 章节状态建议

- `unplanned`：未规划
- `planned`：已规划，待生成
- `draft`：草稿生成中或手写中
- `review_pending`：草稿待审
- `revision_required`：需修订
- `locked`：作者确认锁定
- `synced`：已入库，可作为后续强上下文

### 核心规则

- 只有 `locked` 或 `synced` 章节可以作为强上下文进入长期记忆。
- `draft` 和 `review_pending` 只能作为弱参考。
- `revision_required` 不应自动推进下一章。
- Autopilot 生成后默认进入 `review_pending`，而不是直接等同于“可用章节”。

### 章节审稿面板

每章生成后集中展示：

- 语义完整性：是否截断、是否有阶段性落点。
- 章纲达成度：是否完成本章大纲目标。
- 一致性：人物、地点、关系、设定是否冲突。
- 张力：当前张力等级、缺失元素、修订建议。
- 伏笔：新增、误触发、待回收、已回收。
- 上下文污染：低优先级上下文是否与 Authority Lock 冲突。

### 章节质量结论

输出一个统一判定：

- `pass`：可锁定，可进入下一章。
- `needs_revision`：需要修订，不建议进入下一章。
- `blocked`：严重冲突或截断，禁止入库和继续自动推进。
- `manual_review`：需要作者判断。

## P0：生成前预检

### 目标

在生成前发现高风险上下文，而不是生成后才让用户排雷。

### 预检内容

- 本章权威大纲来源：story_nodes / chapters / 用户输入 / fallback。
- 主角与 POV 锁。
- 上一章结尾状态。
- 本章必须承接的状态。
- 登场角色与地点。
- 待处理伏笔。
- 禁止覆盖设定。
- 冲突/污染上下文。
- token 预算占比：Bible、近章摘要、图谱召回、风格样本、用户指令。

### 交互建议

生成前展示“本章写作依据卡片”，用户可以：

- 确认并生成。
- 移除某条污染上下文。
- 修改本章大纲。
- 切换严格程度。

## P0：一致性问题任务化

### 当前问题

一致性报告如果只显示错误文本，会让用户不知所措。误报也会损害信任。

### 建议结构

每条问题包含：

- 问题类型。
- 严重度。
- 当前文本证据。
- 冲突依据。
- 来源：Bible、章节摘要、三元组、伏笔账本、结构树。
- 置信度。
- 推荐动作。

### 操作动作

- 修正文稿。
- 更新 Bible。
- 接受为新设定。
- 标记误报。
- 忽略此类。
- 重新抽取章节状态。

### 问题收件箱

把所有一致性、张力、伏笔、语义截断问题集中为任务队列，支持按章节、严重度、类型过滤。

## P0：长期记忆入库门禁

### 目标

避免草稿污染后续生成。

### 门禁规则

- 章节未锁定，不写入强长期记忆。
- 章后抽取结果先进入 pending 区。
- 高置信、低风险事实可以自动入库。
- 主角、核心设定、世界规则、时间线变更必须通过校验或用户确认。
- 疑似角色身份漂移进入待确认，不自动写入 Bible。

### 推荐实现分层

- `draft_memory`：草稿弱记忆。
- `pending_memory`：待确认抽取事实。
- `canonical_memory`：已确认强事实。

## P1：Autopilot 双模式

### 定位调整

保留“全托管”能力，但不要把它作为唯一默认体验。Autopilot 应支持两类使用心智：

- 全托管：用户愿意让系统连续推进，适合草稿生产和低风险章节。
- 监管式自动驾驶：系统在关键节点停靠，适合正式连载、长篇核心章节和高一致性要求项目。

### 模式建议

- `全托管草稿`：连续生成并自动推进，但所有产物默认进入待审或弱记忆，不直接锁定为权威。
- `草稿优先`：快速生成草稿，低门禁，生成后待审。
- `质量优先`：生成后自动诊断与修订，不通过则停靠。
- `严格一致性优先`：高风险即停止，必须人工批准。

### 控制台展示

- 当前模式：全托管草稿 / 草稿优先 / 质量优先 / 严格一致性优先。
- 当前阶段：规划 / 预检 / 生成 / 审稿 / 修订 / 入库 / 下一章。
- 当前上下文包。
- 风险提示。
- 下一步动作。
- 最近一次失败原因。
- 可操作按钮：暂停、继续、重写本章、跳过、锁定、回滚。

### 自动停靠条件

监管式模式默认启用自动停靠；全托管模式可配置是否停靠。

- 语义截断。
- 主角/POV 漂移。
- 严重一致性冲突。
- 章纲达成失败。
- 张力低于阈值且本章不是铺垫章。
- 伏笔误回收或新增高风险伏笔。

### 全托管安全边界

- 全托管可以连续写，但默认不自动锁定章节。
- 全托管可以自动入库，但必须由用户显式开启。
- 全托管生成的章节如果命中严重风险，应至少进入 `review_pending` 或 `revision_required`，避免直接污染后续强上下文。
## P1：张力诊断产品化

### 当前方向

张力诊断已经有价值，但要从“报告”变为“改稿工具”。

### 新增判断：张力曲线应前置到结构规划

张力不应被理解为“每章越高越好”。长篇阅读需要铺垫、升温、爆点、余波、转场和缓冲，否则会造成读者疲劳。当前张力诊断偏章后体检，下一步应把张力曲线前置到结构规划阶段：全书曲线 → 每幕曲线 → 每章叙事功能 → 写作执行 → 章后校验。

结构规划时，每幕应生成：

- 幕级 tension curve：开场张力、峰值张力、收束张力、爆点章、缓冲章。
- 幕级 narrative goal：本幕核心冲突、转折、代价、信息揭露和结尾钩子。
- 幕级 handoff：本幕如何把状态交给下一幕。

每章应生成：

- `narrative_function`：铺垫、升温、爆点、余波、转场、反转、揭露、决策等。
- `target_tension`：目标张力档位，而不是统一追高。
- `outline`：100～300 字可执行章纲。
- `must_happen`：本章必须发生的事件。
- `must_not_happen`：本章不得提前泄露或不得改写的内容。
- `handoff_to_next`：章末状态与下一章承接点。
- `pov/characters/locations/foreshadowing`：本章视角、登场角色、地点、伏笔处理。

张力诊断与 Diff 改稿应改为检查“实际张力是否符合计划张力”，而不是简单把低张力都视为问题。比如铺垫章低张力可以通过，高潮章低张力才需要修订。

### 新增判断：幕/章规划需要从标题树升级为写作蓝图

当前结构节点已经具备 `description`、`outline`、`metadata` 等承载字段，幕级规划 prompt 也要求章节返回 `title` 与 `outline`。但从产品体验看，现状仍容易退化成“每幕 + 每章标题列表”，不足以指导真实写作。

下一步应把结构规划产物升级为“幕/章写作蓝图”：

- 幕不只是容器，要有完整梗概、大纲、冲突推进、角色状态变化、张力曲线和收束点。
- 章不只是标题，要有明确写作任务、场景推进、信息增量、人物变化、伏笔动作和下一章交接。
- 生成章节时，后端应强制优先使用 `story_nodes.outline` 作为权威章纲，并将幕级目标、张力目标、章末 handoff 注入 Authority Lock。
- 前端结构树应展示/编辑这些蓝图字段，而不是只展示标题和简短描述。

### 建议能力

- 场景级定位：哪一段松、哪一段冲突弱、哪里代价不足。
- 多版本改写：保守增强、强冲突版、节奏压缩版。
- 改写 diff：显示原文与改写变化。
- 目标感知：铺垫章、过渡章、高潮章使用不同标准。

## P1：上下文卫生可视化

### 目标

让用户知道 AI 为什么这么写，以及哪些上下文不可信。

### 展示内容

- Authority Lock。
- 当前章真实大纲。
- 上章状态。
- 角色锚点。
- 相关地点。
- 相关伏笔。
- 图谱召回关系。
- 冲突上下文。
- 低优先级污染项。

### 交互

- 移除本次召回项。
- 降权某来源。
- 将某条事实标为权威。
- 将某条事实标为污染。

## P1：前端 UI 与交互改造

### 目标

把当前分散在多个 tab 和弹窗里的能力收敛成“本章下一步”导向的工作台。UI 改造不是换皮，而是让用户能看懂状态、风险、依据和可执行动作。

### 章节工作台布局

- 左侧章节树保留，但强化章节状态标签：未规划、待生成、草稿待审、需修订、已锁定、已入库。
- 中间区域聚焦正文：编辑器、生成草稿、改写 diff、保存与锁定。
- 右侧区域改为本章行动栏：写作依据、审稿结果、问题任务、下一步推荐动作。
- 原来的章节状态、章节内容、章节元素可以逐步合并为“章节审稿面板”和“本章上下文面板”。

### 关键 UI 组件

- `Chapter Gate Card`：显示本章是否可进入下一章，以及阻断项/建议项。
- `Context Preview Card`：展示本次生成会使用的上下文包、来源、权重和冲突项。
- `Issue Inbox Panel`：集中展示一致性、张力、伏笔、截断等问题，并提供处理按钮。
- `Revision Draft Diff`：展示 AI 修订草稿与原文差异，用户确认后才采用。
- `Autopilot Mode Selector`：支持全托管草稿、草稿优先、质量优先、严格一致性优先。
- `Autopilot Control Center`：展示当前阶段、上下文包、风险、下一步动作、暂停/继续/回滚。

### 交互原则

- 所有自动修改都先进入草稿或 diff，不直接覆盖。
- 所有入库、锁定、接受新设定都需要明确反馈。
- 所有严重问题都要能跳转到对应正文片段或 Bible/图谱条目。
- UI 应区分“系统判断”和“用户确认”，避免用户误以为 AI 诊断就是最终事实。

### 前端分阶段落地

1. 先增加章节状态标签与本章质量门禁卡。
2. 再把张力诊断、一致性报告、语义截断结果合并到章节审稿面板。
3. 增加问题收件箱和处理动作。
4. 最后重构 Autopilot 控制台与模式选择。

## P2：全书级质量中心

### 能力方向

- 张力曲线。
- 角色弧线。
- 伏笔回收率。
- 设定冲突趋势。
- 章节完成质量趋势。
- 上下文污染趋势。

### 用途

让作者和编辑从全局判断小说是否“长篇跑偏”。

## 指标体系

### 创作效率

- 单章从生成到锁定耗时。
- 每章平均重生成次数。
- 用户每千字手动编辑量。
- 张力改写采纳率。

### 生成质量

- 章节一次通过率。
- 语义截断率。
- 章纲目标达成率。
- 章节锁定率。

### 一致性可信度

- 角色名漂移次数 / 万字。
- 严重设定冲突数 / 章。
- 一致性检查误报率。
- 问题处理完成率。

### Autopilot 健康度

- 连续成功章节数。
- 人工中断率。
- 自动停靠率。
- 自动重写成功率。
- 二次使用率。

## 落地路线图

### 阶段 1：止血与可信基础

目标：先让系统少写坏、少误报、少污染。

交付：

1. 章节状态闭环。
2. 章节锁定机制。
3. 生成前预检卡片。
4. 语义截断门禁。
5. 一致性报告证据链与误报反馈。
6. 章后抽取 pending 区。

验收指标：

- 严重角色名漂移下降。
- 语义截断率下降。
- 误报可统计。
- 未锁定章节不再强污染后续上下文。

### 阶段 2：章节工作台整合

目标：围绕“本章下一步”重组体验。

交付：

1. 章节审稿面板。
2. 问题收件箱。
3. 张力诊断与改写合并到审稿流程。
4. 本章写作依据常驻右侧。
5. 质量结论与推荐下一步。
6. 前端增加章节状态标签、本章质量门禁卡、问题任务入口。

验收指标：

- 单章跨页面跳转减少。
- 问题处理率提升。
- 章节锁定率提升。

### 阶段 3：Autopilot 双模式

目标：同时支持高自动化的全托管和高确定性的监管式自动驾驶，让用户按项目阶段选择控制程度。

交付：

1. Autopilot 模式选择：全托管草稿、草稿优先、质量优先、严格一致性优先。
2. Autopilot 控制台。
3. 自动停靠策略。
4. 高风险章节人工批准。
5. 自动修订与重试策略。
6. 全托管产物默认待审，除非用户开启“自动锁定/自动入库”。
7. 前端提供 Autopilot 模式选择、控制台、自动停靠提示和人工批准入口。

验收指标：

- 连续成功章节数提升。
- 人工中断率下降。
- 自动重写成功率提升。

### 阶段 4：全书级质量与个性化

目标：支持更长篇幅和作者风格沉淀。

交付：

1. 全书质量中心。
2. 角色弧线与伏笔看板。
3. 作者风格画像。
4. 类型模板。
5. 多模型任务路由。

验收指标：

- 10 章、30 章项目留存提升。
- 长篇后期一致性错误不随章节数线性增长。

## 推荐近期实施顺序

1. 章节状态闭环。
2. 章节锁定与入库门禁。
3. 生成前上下文预检卡片。
4. 章节审稿面板。
5. 问题收件箱。
6. Autopilot 双模式控制台与自动停靠。
7. 章节工作台 UI 重组：中间正文、右侧本章行动栏。

## 风险提示

- 如果先重构 UI 而不改数据状态，闭环会停留在表面。
- 如果先继续增强 Autopilot 而没有锁定机制，会继续扩大污染半径。
- 如果一致性检查没有证据链，用户信任会继续下降。
- 如果所有诊断都没有操作按钮，用户会觉得系统只会挑毛病不会解决问题。

## 一句话总结

PlotPilot 下一阶段要从“AI 写作功能集合”升级为“可信长篇创作流水线”。核心不是让 AI 更自由地写，而是让每一章从生成、审稿、修订到入库都可解释、可确认、可追踪。
